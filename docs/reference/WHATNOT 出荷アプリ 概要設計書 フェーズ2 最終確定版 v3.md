# **4. フェーズ2確定設計**

## **4-1. shipping_lines複数ライン時のUI設計**

**✅ 確定**

**前提（設計前提）**

- 管理画面上、配送方法は注文単位で1つに確定して表示される

- 送料と配送方法は独立したロジックで決まる

- 複数候補を並べてスタッフに選ばせるUIは業務上不要。アプリ上も管理画面と同様に注文単位で1つの配送方法を扱う

- パターンA（APIが確定1件を返す）前提で設計を確定。フェーズ3着手前の実機確認により最終確定とする

【運用上の注意】離島判明は配送業者変更のみで対応する軽例外とし、緊急セッション解除はBASE側データ変更（キャンセル・同梱等）が必要な場合のみ使用する。

【現場運用前提】宅配便は原則佐川急便を使用する。ヤマトへの切替は離島判定時または特段の事情がある場合のみ。

**配送業者マッピングテーブル**

| **BASE配送方法名** | **アプリ初期値** | **ロック可能条件** |
| --- | --- | --- |
| 宅配便 | 佐川急便 | マッピング成立 → 選択済み扱い |
| ネコポス・クロネコゆうパケット | ネコポス | マッピング成立 → 選択済み扱い |
| 配送エリア制限商品（大型） | なし | スタッフ手動選択が必要 |
| 配送対象外商品 | なし | スタッフ手動選択が必要 |
| 送料無料 | なし | スタッフ手動選択が必要 |
| 配送エリア制限商品（ガス等） | なし | スタッフ手動選択が必要 |

**上書きルール**

- 「宅配便」→佐川デフォルト。離島アラート発生時または特段の事情がある場合のみスタッフがヤマト宅急便へ上書き

- 「ネコポス・クロネコゆうパケット」→ネコポス固定。上書きは可能だが通常は不要

- マッピング不能の配送方法名が返った場合 → スタッフ手動選択が必要。手動選択完了でロック可能条件を充足

## **4-2. 離島判定の設計**

**✅ 確定**

**2層構造（確定）**

| **レイヤー** | **役割** | **精度** | **求める完全性** |
| --- | --- | --- | --- |
| アプリの離島アラート | 一次スクリーニング | 郵便番号公開リストベース | 不要。気づきの機会を上げれば十分 |
| e飛伝の離島アラート | 最終セーフティ | 佐川の実判定 | こちらが確実な判定 |

**離島判定リスト方針（確定）**

- 初期実装は公開リストベース

- 現場運用で抜け漏れが見つかった場合は随時補完

- 完全性はe飛伝と人間判断に委ねる

**ロック後e飛伝で離島判明した場合の例外処理フロー（確定）**

位置づけ：「配送業者変更のみの例外ルート」。緊急セッション解除・BASE再取得・全体やり直しは行わない。

| **ステップ** | **操作** | **補足** |
| --- | --- | --- |
| 1 | e飛伝で離島アラート発生 | 佐川では対応不可と判明 |
| 2 | アプリ上で該当注文を特定 | セッションロック中のまま |
| 3 | 該当注文の配送業者をヤマト宅急便に変更 | Upstash上の変更のみ。BASE再取得不要 |
| 4 | ヤマト用CSVを再出力 | 佐川CSV出力済みの他注文には影響なし |
| 5 | そのまま作業継続 | セッションロック継続。巻き戻しなし |

**BASE再取得の要否（確定）**

| **ロック後の例外ケース** | **BASE再取得** | **理由** |
| --- | --- | --- |
| e飛伝で離島判明 → ヤマトへ切替 | 不要 | BASE側注文データに変更なし。配送業者変更はアプリ側のみで完結 |
| ロック後に顧客からキャンセル連絡 | 必要 | BASE側で注文変更が発生するため |
| ロック後に同梱要請 | 必要 | BASE側で送料変更が発生するため |

## **4-4. スマレジ在庫表示のスコープ**

**✅ 確定**

**機能の再定義**

「ピッキング前の在庫不足検知」という単一目的ではなく、以下の3つの業務価値を持つ機能として位置づける。

| **価値** | **内容** |
| --- | --- |
| 事前検知 | 在庫不足をピッキング前に把握し、保留・対応判断を早める |
| 優先度判断 | 在庫数と出荷数の関係から急ぎ案件を特定できる |
| 疑似棚卸し | 理論在庫と実在の照合機会になり、在庫ズレを早期発見できる |

**位置づけ（確定）**

- フェーズ3実装対象に格上げ（従来「優先度低」→ 実装必須に変更）

- ピッキング画面（フェーズA）の付帯情報として実装

**表示設計方針**

| **項目** | **内容** |
| --- | --- |
| 表示画面 | ピッキング画面（フェーズA） |
| 表示タイミング | ピッキングリスト初回表示時に在庫数を併記 |
| 表示単位 | 商品・バリエーション単位でスマレジ在庫数を表示 |
| 取得タイミング | ピッキングリスト初回表示時にJANコード→在庫数を一括取得 |
| 更新 | 手動更新ボタンで再取得可能 |

# **5. フェーズBデータフローと状態遷移（確定）**

フェーズ1要件定義書および本フェーズ2議論を統合した確定版。

## **5-1. ステージ構成**

| **ステージ** | **名称** | **概要** |
| --- | --- | --- |
| 0 | セッション復帰 | 再アクセス時にUpstashのセッション状態を確認。アクティブなセッションがあれば自動復帰 |
| 1 | メイン画面表示 | BASE API＋Upstashデータを合成して注文一覧を表示 |
| 2 | 再取得・差分確認 | 出荷準備開始の前提条件。毎回必須 |
| 3 | 注文選択・設定・ロック | 配送業者選択・領収書設定等を行い、出荷準備開始ボタンでセッションロック発動 |
| 4 | 出荷準備・完了処理 | セッションロック中。CSV出力・PDF出力・出荷完了処理 |

**セッションロック発動タイミング（確定）**

セッションロックは「出荷準備開始」ボタン押下時に発動する。注文選択・配送業者選択・各種確認はすべてロック前に実施され、ロック発動時点で選択された注文集合が固定される。

**セッション終了条件（確定）**

セッション対象注文のうち「出荷対象として残っている注文」がすべて出荷完了した時点でセッション終了・ロック解除とする。保留設定された注文およびキャンセルにより除外された注文は、セッション対象から除外されたものとして扱う。除外後の残存注文がすべて出荷完了となった時点でセッションを終了する。

## **5-2. ロック前条件（確定版）**

**ロック可能条件（システムが判定する必須条件）**

| **条件** | **判定方法** |
| --- | --- |
| 対象注文が1件以上選択されていること | UI上の選択状態 |
| 選択された注文がすべてピッキング完了・出荷待ち状態であること | Upstashのピッキングステータス |
| 再取得完了フラグがONであること | Upstashのフラグ |
| 差分確認完了フラグがONであること | Upstashのフラグ |
| 全選択注文の配送業者がマッピング成立またはスタッフ選択済みであること | Upstashの配送業者選択状態 |

**確認項目（人間が判断する情報）**

| **確認項目** | **確認を促すUI** | **進行条件** |
| --- | --- | --- |
| 離島アラート | アラート表示 | スタッフが問題ないと判断すれば進行可 |
| 備考欄・アプリ内メモ | 未読ハイライト等 | 内容確認の上、追加対応不要と判断すれば進行可 |
| 同梱フラグ（同梱しない判断） | フラグ表示 | 同梱しない判断であればそのまま進行可 |
| 領収書設定 | 未設定の明示 | 未設定＝不要として扱い進行可 |

**フラグの成立条件・解除条件（再取得完了／差分確認完了）**

再取得完了フラグおよび差分確認完了フラグは「現在選択されている注文集合」に対して成立する。以下の操作が行われた場合、両フラグは自動的にOFFへリセットされる：対象注文の選択変更（追加／削除）、BASE側データ変更後の未再取得状態、セッション復帰時（再取得未実行の場合）。フラグON条件は、最新データの再取得が完了していること、かつそのデータに対する差分確認が完了していること、の2条件が両立した場合のみ。この2条件が満たされた場合のみ、出荷準備開始ボタンが有効化される。

**チェックシート印刷フラグの有効範囲**

チェックシート印刷済みフラグは「印刷時点の注文内容・配送業者・出荷対象集合」に対してのみ有効とする。以下の変更が発生した場合、フラグは自動的にOFFへリセットされる：配送業者の変更、注文の保留設定、出荷対象注文の変更、CSV再出力（配送内容変更を伴う場合）。フラグOFF時は再印刷を必須とし、出荷完了ボタンは非活性とする。

**shipping_lines前提の扱い**

shipping_linesの仕様については、フェーズ3着手前の実機確認により確定する前提条件とする。本設計はAPIが注文単位で確定1件を返すパターン（パターンA）を前提としているが、実機確認の結果が異なる場合は実装を開始せず、追加設計を行うものとする。

## **7-2. 例外処理フロー一覧**

以下の例外は全てセッションロック前後でフローが異なります。「ロック前に完了させる」が基本原則です。

**① 同梱（ロック前に完了させる）**

| **フロー** | **操作** |
| --- | --- |
| 同梱フラグを確認 | メイン画面で同一顧客名＋住所の注文に同梱フラグが表示される |
| 送料修正 | BASE公式アプリで対象注文の送料を手動編集（片方または両方を0円に） |
| 再取得 | アプリで「再取得」ボタンを押下 |
| 差分確認 | 送料のみ変更を確認 → ピッキング完了ステータスは維持 |
| 継続 | 通常フローへ戻る |

**② 一部キャンセル・丸ごとキャンセル（ロック前に完了させる）**

| **フロー** | **操作** |
| --- | --- |
| BASE側で変更 | BASE公式アプリで商品削除・数量減少・注文キャンセルを実施 |
| 再取得 | アプリで「再取得」ボタンを押下 |
| 差分確認 | 商品明細変更を検知 → 棚戻し指示リストが表示される |
| 棚戻し | 籠から該当商品を取り出し棚へ戻す。対象注文のピッキングステータスがリセット |
| 再ピッキング or 除外 | 一部キャンセル → 再ピッキング後に通常フローへ。丸ごとキャンセル → 出荷対象から除外 |

**③ 離島判明（ロック後・e飛伝での判明）**

| **フロー** | **操作** |
| --- | --- |
| e飛伝でアラート発生 | e飛伝が離島を検知。佐川では対応不可と判明 |
| 該当注文を特定 | アプリ上でロック中のまま該当注文を確認 |
| 配送業者を変更 | 該当注文の配送業者をヤマト宅急便に上書き（BASE再取得不要） |
| CSV再出力 | ヤマト用CSVを再出力。他注文の佐川CSVには影響なし |
| 作業継続 | セッションロック継続。ステップ7（PDF出力）から作業を継続 |

**④ 緊急セッション解除（ロック後の想定外事態）**

| **フロー** | **操作** |
| --- | --- |
| 解除判断 | ロック後にキャンセル・同梱等のBASE側変更が必要になった場合のみ実施 |
| 緊急解除ボタン | 確認ダイアログが表示される。解除理由を入力して実行（ログに記録） |
| BASE側で変更 | BASE公式アプリで必要な修正を実施 |
| ステージ2へ戻る | アプリで再取得 → 差分確認 → 注文選択 → 出荷準備開始（再ロック） |

## **7-3. ロック前判断の具体例**

**進めてよいケース**

| **状況** | **判断** | **理由** |
| --- | --- | --- |
| 同梱フラグが表示されているが同梱しないと判断した | 進めてよい | 同梱しない判断であればBASE側変更なし。再取得済みであればそのまま進行可 |
| 離島アラートが表示されたが既にヤマトに配送業者を変更済み | 進めてよい | 配送業者選択はアプリ側のみで完結。再取得不要 |
| 備考欄に「プレゼント用」と記載があるが対応不要と判断した | 進めてよい | 確認項目は人間が判断。確認済みであれば進行可 |
| 領収書設定が未入力のまま | 進めてよい | 未設定＝不要として扱う |
| 差分なしで再取得完了フラグがONになった | 進めてよい | 差分なしでも手順として再取得を経由済み。ボタンが有効化される |

**注意するケース（対応してからロックする）**

| **状況** | **判断** | **対応** |
| --- | --- | --- |
| 同梱フラグが表示されており同梱すると判断した | 対応してからロック | BASE公式アプリで送料修正 → 再取得 → 差分確認完了後にロック |
| 備考欄に「住所変更あり」「キャンセル希望」等の記載がある | 対応してからロック | BASE側で対応 → 再取得 → 差分確認完了後にロック |
| 配送業者が「要スタッフ判断」のまま未選択になっている | 対応してからロック | 配送業者を手動選択してからロック（ロック可能条件未充足のためボタンが非活性） |
| 離島アラートが表示されており配送業者がまだ佐川のまま | 対応してからロック | 配送業者をヤマトに変更してからロック |
| ピッキング未完了の注文が残っている | その注文は選択不可 | ピッキング未完了の注文は選択できない。完了を待つか今回の出荷対象から外す |
