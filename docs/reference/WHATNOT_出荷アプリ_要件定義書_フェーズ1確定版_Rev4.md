# **1. 本文書について**

本文書は、WHATNOT HARDWEAR STOREのBASE出荷業務シームレス化アプリ開発プロジェクトにおけるフェーズ1（要件定義）の確定内容を記録したものです。

本Rev.4は、Rev.3に対して以下の2点を追加した最終確定版です。①セッション途中離脱時の復帰仕様（Upstashによるサーバー側セッション保持・再アクセス時の同一セッション復帰・他スタッフからの復帰）、②出荷準備開始前の再取得強制条件（毎回再取得を必須とし差分確認完了後にのみ出荷準備開始を許可する制御）。

本文書は監査・照合目的で使用されることを想定しています。

# **2. 背景・現状課題**

## **2-1. 現状のオペレーション**

WHATNOT HARDWEAR STOREは工具・アウトドア用品を扱う直営実店舗兼オンラインショップで、BASEでECを運営している。実店舗とオンラインショップで在庫を共有している。

現状の出荷業務フローは以下の通りで、全て別操作・別ダウンロードで寸断されている。

- BASE管理画面から注文データをCSVダウンロード

- ExcelマクロでピッキングリストをPDF作成・印刷

- BASEアプリで納品書をダウンロード・印刷

- 配送形態別にCSVを出力

- 佐川急便／ヤマト運輸のシステムへCSVを取り込み

- 出荷後にBASE管理画面でステータスを手動変更

- 送り状番号をBASEに手動コピペ

## **2-2. 業務スケール**

| **項目** | **内容** |
| --- | --- |
| 通常注文件数 | 5〜10件/日 |
| 繁忙期注文件数 | 最大50件（過去100件超あり） |
| 佐川：ヤマト比率 | 約8：2 |
| 出荷作業時間帯 | 11:00〜13:30 |
| 集荷タイムリミット | 13:30〜14:00（佐川） |
| データ処理時間（現状） | 約30分以上（梱包除く） |

## **2-3. 現状の問題点**

- 作業が複数システムにまたがり、寸断されている

- 紙ベースのピッキングリストによるミスリスクがある

- 送り状番号の手動コピペによるミスリスクがある

- スタッフ不在時に同品質の出荷対応ができない

- ピッキングミス・数量ミス・同梱漏れが発生しうる

- 出荷ステータス更新の抜け漏れが発生しうる

# **3. 設計理念**

***「スタッフが誰でも使えて、人的ミスが構造的に発生しない出荷業務システム」***

具体的には以下の3点を核心的な設計目標とする。

- 岡本スーパーバイザー不在時でも同品質の出荷対応が可能であること

- ピッキングミス・数量ミス・同梱漏れを設計で防ぐこと

- 発送済み注文の二重処理・未発送なのに発送完了にするミスを構造的に排除すること

# **4. 確定業務フロー**

業務フローを以下の2フェーズに分割する。この分割は「作業の性質が根本的に異なる」「使用端末が異なる」「認知コストを下げる」という理由から確定した。

## **フェーズA：ピッキングフェーズ（スマホで完結）**

特徴：独立したフェーズ。出荷準備フェーズとは切り離されており、随時実行可能。ロックなし。

- BASE公式アプリの注文通知を受けたスタッフがスマホでアプリを開く

- トータルピッキングリストがリアルタイムで画面に表示される（未対応注文の全商品合計）

- スタッフは必要商品をバーコードスキャンして個数を入力

- スキャンした商品は時系列順に注文へ自動割り当て

- 全商品の割り当てが完了した注文が「ピッキング完了」ステータスに自動更新

- ピッキング完了した商品は物理的に梱包作業エリアの籠へ移動

## **フェーズB：出荷準備フェーズ（PCメイン）**

特徴：注文選択時点でセッションロックが発動する。以降は選択された注文が完了まで固定される。

- PCでアプリのメイン画面を開く

- 未対応注文が一覧表示される（ピッキング完了・未完了・保留中・キャンセル済みを色分けで表示）

- 同梱フラグを確認し、必要に応じてBASE公式アプリで送料修正→アプリで再取得→差分確認

- 【必須】出荷準備開始前に対象注文データの再取得を実行。再取得完了・差分確認完了後でないと出荷準備開始ボタンは有効にならない

- 再取得後の差分処理：送料変更のみ→ピッキング完了ステータス維持／商品明細変更→ピッキングリセット・棚戻し指示／注文キャンセル→対象から除外

- 各注文のBASE配送方法（デフォルト値）を確認。離島アラートやネコポス不可等の判断をした上で配送業者を選択・上書き

- 各注文の備考欄・アプリ内メモを確認

- 領収書要否を確認しチェック・宛名入力

- ピッキング完了済みの注文のみ選択可能

- 「出荷準備開始」ボタン押下でセッションロック発動

- 配送会社別CSV出力 → 各社システムへ取り込み → 送り状印刷

- 納品書・領収書PDFを出力 → 印刷 → 同梱

- 送り状番号を入力（任意）

- 最終確認チェックシートPDF出力・印刷 → 送り状貼付済みの箱を目視確認（注文ID・注文者名・配送業者）

- チェックシート印刷完了後に出荷完了ボタンが有効化される

- 出荷完了処理 → BASE APIでステータス更新・送り状番号記録

- セッション終了・ロック解除

# **5. セッションロック設計（最重要機能）**

セッションロックは本システムの根幹をなす最重要機能である。以下の2つの最大リスクを構造的に排除するために設計された。

- 発送済みの注文を再度ピッキング・出荷対象に含めてしまうこと

- 未発送にもかかわらず発送完了ステータスにしてしまうこと

| **項目** | **内容** |
| --- | --- |
| ロック発動タイミング | 出荷準備フェーズで「出荷準備開始」ボタンを押した時点 |
| ロック内容 | 選択された注文セットを固定。他デバイスからの変更・二重処理を防ぐ |
| 新規注文の扱い | ロック後に入った新規注文はそのセッションに混入しない |
| デバイス間同期 | Upstash Redis/KV（Vercel Marketplace連携）にセッション状態を保存。PC・スマホで同一状態を参照 |
| セッション保持場所 | サーバー側（Upstash）に保持。ブラウザを閉じてもセッションは消えない |
| 途中離脱時の復帰 | ブラウザ閉じ・PC落ち・スタッフ交代が発生した場合、再アクセス時に同一セッションへ自動復帰。他スタッフが別端末からアクセスした場合も同一セッションへ復帰可能 |
| ロック解除タイミング | 全注文の出荷完了処理が完了した時点 |
| 緊急セッション解除 | やむを得ない事情（ロック後のキャンセル・同梱等）が発生した場合のみ。確認ダイアログ表示後にロック解除。BASE側で変更→再取得→再度注文選択→セッションロックの手順でやり直し |
| 保留機能 | セッション中の注文を個別に保留設定可能。理由メモを記録 |

## **5-1. セッションロック前に完了させる処理**

以下の処理は全てセッションロック前に完了させる運用とする。

- 同梱処理（送料変更・再取得）

- 顧客申し出による一部商品キャンセル・数量変更

- 注文丸ごとキャンセル

- 上記後の注文データ再取得と差分確認

## **5-2. 出荷準備開始前の再取得強制条件**

BASE APIはWebhookに非対応のため、アプリがBASE側の変更をリアルタイムで検知することはできない。この制約を踏まえ、以下の制御を設ける。

- 出荷準備開始ボタンを押す前に、対象注文データの再取得を必須とする（毎回強制）

- 再取得後、差分確認ステップを完了しないと出荷準備開始ボタンは有効にならない

- 差分なしの場合もそのまま進行可能。手順として再取得・差分確認を必ず経由させる

- 同梱・キャンセル・数量変更等のBASE側注文修正は全てセッションロック前に完了させる運用とする

再取得後の差分処理ルール（既存定義と同一）：

- 送料のみ変更（同梱）→ ピッキング完了ステータスを維持

- 商品明細変更（一部キャンセル等）→ ピッキングステータスをリセット・棚戻し指示リストを表示

- 注文丸ごとキャンセル → 出荷対象から除外・棚戻し指示リストを表示

## **5-3. 注文一覧の表示ステータス**

| **ステータス** | **内容** | **選択可否** |
| --- | --- | --- |
| ピッキング完了・出荷可能 | 通常の出荷対象 | 選択可 |
| ピッキング完了・保留中 | 住所未定・先方連絡中等の理由で今回は出荷しない | 選択不可（保留中として色分け表示） |
| ピッキング未完了 | まだピッキングが終わっていない | 選択不可 |
| 積み残し保留 | 前回セッションで保留になったまま持ち越し | 選択不可（保留中として色分け表示） |
| キャンセル済み | dispatch_status:cancelledの注文。BASE側操作の反映確認のため表示 | 選択不可（キャンセル済みとして色分け表示） |

## **5-4. 再取得時のピッキングステータスの扱い**

| **変更内容** | **ピッキングステータス** | **理由** |
| --- | --- | --- |
| 送料のみ変更（同梱） | 維持 | 商品は変わらないため再ピッキング不要 |
| 商品明細変更（一部キャンセル等） | リセット | 棚戻し指示リストを表示。物理的な棚戻しが必要なため |
| 注文丸ごとキャンセル | 対象から除外 | 出荷対象外。棚戻し指示リストを表示 |

# **6. 同梱・キャンセルフロー（Rev.2追加）**

## **6-1. 同梱フロー**

同梱の発生条件（業務ルール）：

- 対象：同日注文・同一顧客（名前＋住所が一致）の複数注文のみ

- 注文者情報が異なる場合は申し出があっても同梱しない

- 発生頻度：稀だが定期的に発生しうる

同梱時のオペレーション：

- アプリがメイン画面（注文一覧）で同梱フラグを表示

- スタッフが同梱するか判断

- 同梱する場合、BASE公式アプリで送料を手動編集（片方または両方を0円に）

- 編集後、アプリ上で「再取得」ボタンを押下

- 差分検知：送料変更のみ確認→ピッキング完了ステータスを維持したまま送料を更新

- 再取得後、出荷準備を継続

## **6-2. キャンセルフロー**

一部キャンセル・丸ごとキャンセルのオペレーション：

- 顧客申し出等によりBASE公式アプリで注文を変更（商品削除・数量減少・注文キャンセル）

- アプリ上で「再取得」ボタンを押下

- 差分検知：商品明細の変化を検知

- 棚戻し指示リスト（商品名・バリエーション・数量・注文ID）を画面表示

- 対象注文のピッキングステータスをリセット（棚戻し後に再ピッキングが必要）

- 丸ごとキャンセルの場合は出荷対象から除外

## **6-3. 保留注文の管理**

保留注文発生時のオペレーション：

- 保留設定時にアプリが確認画面を表示（注文ID・顧客名・保留理由・対象商品リスト）

- スタッフは共有ピッキング籠から該当商品を取り出し、注文ごとの別カゴに移し替える

- 別カゴに貼付する識別ラベル（注文ID・顧客名・保留理由・日付）をアプリからPDF印刷して貼付

- 商品は売り場（棚）には戻さない。他の顧客に購入されるリスクを防ぐため

- 保留が解除されて出荷可能になった際は、識別ラベルを納品書と差し替えて出荷フローへ復帰

- 保留解除時、商品は梱包エリアにあるためピッキング完了ステータスを維持する

| --- | --- | --- | --- |

| 11 | **出荷保留** | セッション中の注文を保留設定。理由メモをアプリ内に記録。次回セッションで再判断 | 在庫不足・住所不明等で出荷できない注文を適切に管理するため |

| 18 | **在庫数表示** | スマレジAPIから該当商品の在庫数を取得・表示（優先度低） | ピッキング前に在庫不足を事前検知したいため（スマレジリテールビジネスプランでAPI利用可能） |

| 20 | **商品名固定** | ヤマトCSV向けに商品名を「WHATNOT HARDWEAR STORE ご購入商品」で一律固定 | ヤマトCSVの商品名カラムは1行制限のため長い商品名が入らないため |
| 21 | **アプリ内メモ** | 注文ごとに保留理由・引き継ぎ事項等をアプリ内（Upstash KV）に保存・表示 | BASE APIで注文メモの読み書きができないため、アプリ内で代替管理する |

## **7-3. スコープ外（将来拡張候補）**
